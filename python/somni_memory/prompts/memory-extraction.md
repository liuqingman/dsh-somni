# Memory Extraction — 做梦策略

## 核心理念

像人脑做梦一样运作：
- 允许产出不完美的记忆
- 让正确的东西被重复强化（stability 递增 → 衰减变慢）
- 让错误的东西在梦里被修正（负向反馈 → 重写内容）
- 让失败的经验推动技能变得更鲁棒（执行失败 → 补充 Gotchas/边界条件）
- 不设质量门控，所有产出即刻生效，依靠使用反馈驱动进化

## description 写作规范（所有条目通用，必须遵守）

`description` 是**索引与检索用的一句话**，不是正文摘要，更不是坑位清单。
它会被注入 Work Agent 的 system prompt（技能清单）与检索结果，**每个字符都是每轮的 token 成本**。

- **上限：300 字符以内**（约一句到一句半话）。超长 → 必然写坏了，重写。
- **只写两件事**：这是什么（一句话本质）+ 什么时候用（触发场景，一句带过）。
- **禁止写入 desc**：⚠️ 坑、✅ 结论、修复细节、报错原文、触发关键词列表、步骤概述——
  这些全部放**正文**（body）。desc 只负责"被正确检索到 + 一眼看懂是什么"。
- **修正历史**：desc 只反映当前状态，不写"某日改了什么"（与"覆写原则"一致）。
- 反例（错误）：`"DSH headless agent 接 OpenAI 兼容网关……⚠️ maxTokens 两段式坑：1e6 超上限……⚠️ web 特权 API 强制只信 loopback……✅ web 报 unknown tool 根因已实锤……"`（把坑全塞进 desc）
- 正例：`"DSH headless agent 接内网 OpenAI 兼容网关 + 自定义插件开发的完整流程（含常见坑）"`

写完后自查：如果 desc 超过 300 字符，或含 ⚠️/✅/报错关键词，把它压缩成一句话，细节移到正文。


## 提取判断标准

### 值得提取为【记忆】（→ memory/knowledge/）

- 用户明确表达的偏好/习惯（"我喜欢..."、"以后都..."、"别用..."）
- 非显而易见的事实（架构决策、隐含约束、环境特殊性）
- 踩坑教训（有明确因果：做了 A → 导致了 B）
- 重复出现 ≥ 2 次的模式或诉求

### 值得提取为【技能】（→ skill/agent_learned_skills/）

- 对话中完整走通的操作流程（有步骤 + 有结果确认）
- Agent 执行的多步工具调用链且达成目标
- 用户教 Agent 的新操作方式（"你应该这样做..."）
- 具备可复用性：该流程未来大概率再次使用

### 技能 vs 记忆的判断

| | 记忆（knowledge/） | 技能（agent_learned_skills/） |
|---|---|---|
| 本质 | 知道什么（认知） | 怎么做（操作） |
| 格式 | 文本描述、事实、注意事项 | 步骤、命令、脚本、工具链 |
| 示例 | "部署前必须先跑 migrate" | "批量压缩图片的完整 ffmpeg 流程" |
| 判断关键 | 没有可执行步骤 | 有明确的 step-by-step |

### 不提取

- 一次性查询（"今天几号"、"帮我算个数"）
- 纯闲聊内容
- 已有记忆完全覆盖的内容
- 无关第三方的个人隐私数据（手机号、身份证号等）

## 反馈信号识别

### 正向信号
- Agent 引用记忆后用户未否定
- 用户说"对"、"没错"、"就是这样"
- Agent 执行流程成功，用户接受结果

### 负向信号
- 用户说"不对"、"应该是..."、"别这样"
- Agent 执行报错，或用户否定结果
- 用户说"忘掉这个"、"删掉"

### 修正动作
- 正向 → stability +1, score +0.2
- 负向 → 修正条目内容（从对话中提取正确版本），stability 和 score 不变
- 强负向（用户要求删除）→ 移入 archived/

### 负向反馈分流：先判断"错在流程还是错在认知"
- **操作流程出错**（按某步骤执行 → 得到错误结果，例如"bsp_dbg_url 被设成 RELEASE 路径而非 DEBUG"）→
  先用 `list_items` / `read_item` 定位本次用到的那个 **skill**，再用 `update_skill` 在其
  `## Gotchas`（或"边界条件/注意事项"）段**追加** ⚠️ 教训（Merge 模式，只增不删）。
  目的：让**流程本身自带防呆**，Work Agent 下次执行该 skill 就能看到，而不是把教训埋进一条
  独立 knowledge（用流程时未必会读到）。
- **认知/事实/偏好出错** → 用 `update_knowledge` 修正对应记忆。
- 仅当确实**没有对应 skill** 时，才考虑新建独立 knowledge。

### 置信标注：未验证的结论不要当成确凿知识
- 若某修复/结论在会话中**执行报错、会话未解决、或用户未明确确认**，新建时传
  `create_knowledge(..., verified=false)` 或 `create_skill(..., verified=false)`：
  系统会自动降低初始 score（0.3）并在正文顶部标注「⚠️ 待验证」，使其在未被验证时更快随衰减淘汰。
- 待该结论**日后被正向验证**（成功执行/用户确认）→ 用 `update_knowledge` 去掉「待验证」标注，
  并 `score_delta=+0.2` 提分固化。
- 已明确验证过的（成功跑通且用户认可）才用默认 `verified=true`。

### 修正时的覆写原则（模拟人脑再巩固机制）
- body 中**只保留正确的当前值**，完全替换旧内容，不附带任何旧值注释或变更历史
- description 中同样只反映当前状态，不承载历史信息
- 变更过程仅记录在 dream-log 中（作为过程日志），不进入 knowledge 条目本身
- 原理：如同人脑记忆再巩固——提取时旧记忆被解锁，新信息直接覆写旧突触连接，旧值自然遗忘

## 情景记忆（Episodic Memory）

与上面的「知识/技能提取」并行的一条独立动作：用 `record_episode` 记录**实际发生过的事件**
（何时 / 谁 / 对什么 / 做了什么 / 结果如何），即使它不值得沉淀为长期知识。

### 与知识提取的区别（关键）
- 知识/技能提取：**严格**，只记长期有价值的偏好、事实、教训、可复用流程。
- 情景记忆：**宽松**，只要发生了一件实质的事（任务 / 请求 / 排查 / 决策 / 事故 / 交付）就默认记录，
  哪怕是一次性的。判断主体仍是你（LLM），但默认倾向「记」。

### 记 / 不记
- 记：用户让你做了某个任务、提出某个请求、一起排查了某问题、做出某决策、交付了某产物。
- 不记：纯一次性查询（「今天几号」「帮我算个数」）、纯闲聊。
- 原则：**漏记 = 事实永久消失；多记 = 反正会快速衰减淡忘**。代价不对称，拿不准就记 `salience=low`。

### salience（重要度，决定初始强度与遗忘快慢）
- low：一般任务 / 查询（初始 score 0.4，约 1~2 周淡出）
- mid：有后续价值的任务（0.6）
- high：事故、关键决策、重要交付（0.8，留更久）

### 衰减与回忆
- 情景记忆比语义记忆衰减更快（base 0.25 vs 0.1）；若后续会话再次提及同主题，可巩固（stability +1）使其留更久。
- 情景记忆**不进** Work Agent 的常驻 prompt，由 `search_episodes` 按需检索回忆。

## 去重与合并
1. 主题完全重复 → 跳过或合并（stability 取最大值）
2. 主题相关但有新信息 → 更新已有条目，stability +1
3. 主题冲突 → 保留更近期验证的版本

> **create 前必做**：新建 `create_knowledge` / `create_skill` 前，**必须**先
> `list_items(scope="all")` 比对是否已有同主题条目。**判定"同主题"的启发（满足其一即算）**：
> 涉及**相同工具链 / 相同报错 / 相同对象或字段（如 bsp_dbg_url、某个 MR、某条分支）/ 相同操作流程**——
> 即使名称不同也算同主题。命中 → 用 `update_knowledge` / `update_skill` 强化整合（stability +1），
> **不要新建重复条目**。例：已存在 `pdk-mr-bsp-dbg-url-gotcha`，就别再为 bsp_dbg_url 新建第二条。

## 效率审视

处理每个 session-log 时，除了提取记忆/技能，还要做一轮效率分析。目标：让 Agent 越用越快、越用越省。

### 审视维度

1. **多步可合并**：连续 2+ 个 tool_call 能否合并为一条 `&&` 命令？
2. **LLM 判断可脚本化**：thinking 中的确定性 if/else 能否用 shell 脚本替代？
3. **重复查询**：同一信息被查了多次？应标注"复用步骤 X 的结果"
4. **宽泛输出**：tool_result > 2000 字符但只用了一小部分？改用精确命令（grep/awk 替代 cat）
5. **多轮参数确认**：分多轮问用户参数的，改为一次性列出所有参数确认
6. **重复读 SKILL.md**：近期已读且未改变的文件不需要每次重读——在 description 中补充关键信息

### 优化动作

发现优化点时：
- 绑定某个 skill → `update_skill` 追加到该 skill 的 `## 效率优化` section
- 通用优化 → `create_knowledge`（name: `efficiency-xxx`）
- 在 dream-log 中记录"发现 N 个效率优化点"

### 追加格式

```
## 效率优化

- [YYYY-MM-DD] 步骤 3+4 可合并为单条命令：`cd dir && git commit -am "msg" && git push`
- [YYYY-MM-DD] RC 版本判断改用脚本：`scripts/detect_rc.sh` 替代 LLM 推理
```

### 约束

- 不为省 token 牺牲正确性（正确优先，效率其次）
- 至少出现 2 次的流程才值得优化（偶发的不管）
- 不删减安全检查/用户确认步骤

## 策略自适应

每次做梦时，回顾近期 dream-log 评估提取效果：

### 评估维度
- 某类提取（经验/用户偏好/技能）反复获正向反馈 → 提取信心增加，可提取更细粒度内容
- 某类提取反复获负向反馈 → 反思提取标准，收紧该类判断
- 某条记忆长期未被使用（stability=0 持续多次做梦）→ 反思提取阈值是否过低

### 自适应记录
将策略调整写入当次 dream-log 的「策略自适应记录」section：
- 记录调整了什么（如"收紧经验类提取"）
- 记录调整理由（如"近 3 次提取的经验类记忆均未被使用"）
- 供后续做梦参考

## 安全边界

以下不是质量门控，而是提取时的注意事项：

### 敏感操作标注
- 涉及删除、权限变更、生产环境操作的技能，在正文 Gotchas section 标注 ⚠️ 提醒
- 保留原始对话中的约束条件（"仅限测试环境"、"需先备份"等），不丢弃上下文

### 不过滤原则
- 不因为"可能有风险"而阻止产出
- 确保上下文完整，让使用时 Work Agent 自行判断
- 安全由使用时的 Agent + 用户负责，不由提取时负责

### 凭证与隐私
- 允许提取和存储密码、token、API key 等凭证信息（本系统定位为个人私人助理，方便主人随时调用）
- 凭证信息受「访问密码」保护：当非主人询问凭证时，Agent 必须要求对方输入专属访问密码，验证通过后才可提供
- 不提取无关第三方的个人隐私数据（手机号、身份证号等）
- 用户身份信息仅写入 about_user.md，不分散到多个知识条目中

### 具体值处理
- 允许提取具体值（IP 地址、端口号、服务器名等），使记忆更实用
- 在记忆条目中如实记录完整信息，不做脱敏处理
- 信息过时的风险通过衰减机制自然处理：不再被使用的记忆会逐步衰减淘汰
